# Combat Utility V4: character mechanics

The optimizer reads numeric effects from a pinned game-data snapshot and evaluates each character's kit. The bundled library covers **341 obtainable characters and 1,564 named abilities**; the current operation inventory is in the coverage table. The source is [swgoh-utils/gamedata](https://github.com/swgoh-utils/gamedata/tree/8d86d7002e8cab5839f04540d93ac303db078517). This is extracted game data distributed by that project, not a developer-published battle simulator.

The [coverage table](../reports/characterKitAnalysis.md) lists every character. The [full analysis](../reports/characterKitAnalysis.json) retains each ability's localized description, maximum description, numeric coefficients, targets, prerequisites, triggers, context queries, and exact omitted effect IDs/reasons. Every referenced effect graph is traversed; cyclic branches are recorded rather than followed indefinitely. The smaller runtime library comes from this same analysis.

## What contributes to utility

The model evaluates Physical/Special damage coefficients, Max Health/Protection and target-Health attacks, normal/noncritical/guaranteed critical attacks, basic and special rotations, mitigation, resistance, recovery, Health Steal, buffs/stat changes, turn meter, assists, counters, bonus actions, control, dispels, and stat sharing. Conditional effects use explicit assumptions. Examples include Grievous's Health attacks, Embo's Protection attack, Hermit Yoda's healing and trained-ally assists, Barriss's Health-dependent recovery, and R2's faction bonuses and sharing.

For each opponent scenario, `U = team damage rate × team effective HP`. Healing and Protection recovery contribute to effective HP over a bounded battle horizon, using expected missing-pool fractions. Control and removed enemy TM reduce incoming pressure. Resistance affects resistible effects and lost output from incoming control. Team allies use their own kits and actual equipped stat snapshots. R2's Number Crunch is evaluated once, including when R2 is a teammate.

Enemy Offense changes affect incoming damage. Healing immunity/Shock prevent the assumed enemy recovery; ability block, Daze, Shock and buff immunity use editable enemy special/assist/TM/buff assumptions. These values describe the expected opponent behavior and are not hidden character weights. Direct damage does not test Potency/Tenacity; resistible debuffs and their attached effects do.

Specials have expected frequencies based on their cooldowns; the remaining actions use the basic. This is an expected-value rotation, not ability AI. Extra unlock-dependent abilities are disabled by default. Set their expected use count only when unlocked. Ability levels use the maximum non-Omicron tier. The model does not read individual ability upgrades from the imported roster.

Three editable default opponents cover neutral, tougher/faster, and lighter opponents with Protection bypass. They are illustrative scenarios, not a claim to represent particular live meta teams. All weights, incoming control loss, battle length, missing pools, state counters and effect probabilities are assumptions visible in the editor and exports.

When no manual teammates are selected, the app searches game-provided example squads containing the character and selects the one with the most members available in the roster. Missing allies are omitted; their stats are never invented. The example squad's available leader supplies the leader ability. You can select up to four allies, choose a leader, or turn off automatic teams. These snapshots remain fixed while the optimizer changes the selected character's mods; this is not joint squad optimization.

## Stat units and search

Pruning uses `sum(actual mod stat amount × d log(U)/d stat point)`. Health/Protection, damage, raw defense and Speed use their native points; percentage stats use percentage points. V5 display priorities compare representative mod-sized increments and never enter finished-set scoring; see [the V5 changes](combat-utility-v5.md).

The derivative reference is the character's equipped complete set, projected with the run's upgrade settings. Finished sets use complete stat vectors and native bonuses in exact evaluation of this model. The search prunes and performs bounded refinement, so it is not an exhaustive six-mod search. Normalized score is `100 × U(candidate)/U(unmodded character)` with teammates held fixed. Scores of different characters cannot be summed into roster strength.

Performance caches preserve the existing search. Each character/model/baseline evaluates its unmodded reference once and reuses scores for identical full stat vectors. Only 8,192 scalar results and 64 detailed scenario results are retained per context; caches reset between characters. Audit entries still distinguish different mod IDs with identical stats. Kit operations are indexed by kind, identical selectors share their matching work, and query/basic-attack results are reused only while their inputs remain unchanged. Stats and turn-rate changes invalidate the corresponding phase caches.

The app and worker load **`src/constants/generatedCombatPrograms.json`**, a generated preprocessing artifact. It contains operation phase lists, default rotations, classified effect tags, stat/query mappings, and currently 2,898 deduplicated target selectors with precomputed character eligibility. `generatedCharacterKits.json` remains the canonical source library for analysis and generation. Preprocessing and the fast scorer preserve the compiled mechanics and their explicit coverage gaps.

One preparation pass binds each selected team/leader/opponent to those programs. Fixed recipient relationships and count queries are reused across candidates. The scoring path drops branches whose fixed conditions cannot contribute, while keeping stat-dependent queries, resistance, caps, sharing, healing, and conditional rate changes dynamic. It returns numeric U; full diagnostics are produced on demand for audit entries and reports. Marginal calculations also use this numeric path. Changed assumptions, team snapshots or opponents invalidate preparation even when their objects are edited in place.

The program file is shipped with the app. `npm start` and `npm run build` verify its source/compiler hashes and regenerate it offline only when needed. No source download is required. Maintainers can run `npm run kits:preprocess` explicitly. The run report records the preprocessing version and hashes so its calculation path is identifiable.

`npm run optimizer:performance-test` compares cached and uncached calculations across every kit, teams, multiple stats/states, and matchups, and checks worker cache isolation/auditing. `npm run optimizer:benchmark` runs a deterministic Hondo/Pirate squad with 192 synthetic mods. Set `BENCH_CHARACTERS` to a comma-separated list for additional characters. Results depend on hardware, inventory and chosen team; the [performance report](../reports/optimizerPerformance.md) records the measured fixture.

`npm run optimizer:preprocessing-test` additionally compares the artifact and both scoring paths against a maintained raw-kit reference interpreter for all 341 kits. It checks deterministic regeneration, artifact freshness, cold/warm plans, edited model invalidation and synchronized worker files. This verifies preprocessing equivalence, not independent correctness of every mechanic.

## Limits and auditability

Reading all kits does **not** mean every battle mechanic is fully simulated. Summons, ability AI, dynamic stack evolution, cooldown resets, unique immunity state, defeat prevention, mode-specific Omicrons and complicated trigger chains can require a stateful simulator. Unsupported branches are explicit in the analysis. Unspecified counters and tags contribute zero to their conditional branch and appear under `unresolvedStates` in run exports. The editor accepts `blackboards` and `stateTags`, keyed by character ID, for explicit counts/probabilities. Those inputs affect supported queries; they cannot implement omitted operations.

For example, Profit-dependent Hondo branches are incomplete without their counter/effect assumptions. A recommendation must not be interpreted as a full battle estimate simply because the kit was ingested. Omitted-effect counts also include non-scoring operations such as visual/script effects. They measure branches, not percentages of gameplay fidelity. Current assumptions about duration, healing availability and incoming control can materially change set recommendations.

The saved run retains full mechanics diagnostics. The default compact analysis export keeps source revision/hash information, resolved team and assumptions, before/after roster stats and scores, marginal scoring priorities, damage/action rate/EHP/healing/Protection recovery/assist summaries, control contribution, coverage counts, and counts plus ten samples of unresolved states per scenario. It keeps five top candidates and numeric scores for every evaluated loadout, including Health alternatives. Repeated reference/team stat vectors, per-candidate combat diagnostics, full state traces, secondary mod details and duplicate targets are omitted. Messages and missed goals are limited to twenty per character. Exporting an existing run again produces the compact file without rerunning optimization. Kyber frequencies remain diagnostic only.

## Refresh and verification

Restart the app and optimize again. No source download or data-generation script is needed: the generated kit library is bundled, and `npm start`/`npm run build` copy all three worker dependencies automatically. Previous scoring caches are invalidated; old Combat Utility and Kyber selections upgrade automatically. Edited matchup values, manual teams and custom linear plans are retained.

For maintainers, `npm run kits:fetch` downloads the latest upstream snapshot and records its immutable commit and SHA-256 hashes. `npm run kits:compile` recompiles the analysis/runtime library offline. Inspect the changed source and report before adopting a new revision. `npm run kits:test`, `npm run combat:test`, and `npm run meta:test-v2` check roster-wide finite utility, representative mechanics, worker parity, native bonuses, saved migration, request validation, and report output. `npm run build` checks the app bundle.
